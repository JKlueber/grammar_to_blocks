\begin{abstract}
Model checking is an automatic technique for verifying correctness properties of safety-critical reactive systems. LTL is a popular logic for the specification of correctness properties. NuSMV is a classic model checking tool supporting the analysis of transition systems and LTL specifications.

We develop a methodology and tools for semantically comparing NuSMV specifications. The input of our tool are two LTL specification and a model. Our tool checks refinement, equivalence, or incomparability of the provided specifications.
\end{abstract}

\subsection{Motivation}

When developing safety critical or high-assurance systems LTL specifications become artifacts of the software engineering life-cycle. The specifications have to be written, maintained, updated, refactored etc. as the software system is created and evolved. Writing and reading LTL specifications is a non-trivial task. To date there are no tools that support the semantic comparison of LTL specifications as a system evolves. We aim to develop a methodology and tools for semantically comparing NuSMV specifications to support software engineers writing and maintaining LTL specifications.

\section{Problem Statement}
The input of our tool are a model $\mathcal{M}$ and two LTL properties $\phi$ and $\psi$. 

The possible outputs of a semantic comparison are:
\begin{description}
\item[$\phi$ refines $\psi$] iff $\forall \pi \in \mathcal{M}. (s \models \phi) \rightarrow (s \models \psi)$ denoted $\phi \prec \psi$
\item[$\psi$ refines $\phi$] iff $\forall \pi \in \mathcal{M}. (s \models \psi) \rightarrow (s \models \phi)$ denoted $\psi \prec \phi$
\item[equivalent] iff $\phi \prec \psi$ and $\psi \prec \phi$ denoted $\phi \equiv \psi$
\item[incomparable] otherwise
\end{description}

Optionally, we want the tool to ignore the model $\mathcal{M}$ and perform the semantic comparison for all possible models.

\section{Example \& Intuition}
Consider the example model of a simple request answering system. The engineers initially formulated the LTL specification \texttt{eventuallyBusy} in lines 12-13 stating that incoming requests will eventually be worked on in state \texttt{busy}. After carefully checking the implementation the team wants to strengthen the specification to require that the \texttt{busy} state is reached immediately or in the next step (see lines 15-16).



\begin{lstlisting}[caption=NuSMV model example with two named LTL specifications to compare, label=lst:example]
MODULE main
VAR
  request : boolean;
  state   : {ready, busy};
ASSIGN
  init(state) := ready;
  next(state) := case
       state = ready & request : busy;
       TRUE                    : {ready, busy};
  esac;

LTLSPEC NAME eventuallyBusy :=
  G(request -> F state = busy)

LTLSPEC NAME nowOrNextBusy :=
  G(request -> (state = busy | X state = busy))
\end{lstlisting}

\subsection{Limitations of the Implementation}
Our implementation uses regular expressions to find \texttt{LTLSPEC} blocks within a NuSMV file. In cases where the LTL formula is not terminated with a semicolon or where it contains comments that include a semicolon our approach might not capture the correct formulas. Right now there is no easy mitigation of this limitation other than making sure about the above. An alternative implementation should have been based on a NuSMV parser instead of using regular expressions.

When checking semantic properties of specifications without considering the model our implementation attempts to comment out \texttt{ASSIGN}, \texttt{TRANS}, \texttt{INIT}, and \texttt{INVAR} blocks. Again we identify these blocks using regular expressions, which is prone to the same errors mentioned above. We have decided to follow this approach rather than extracting the variables as the NuSMV files might declare and compose multiple modules whose structure must be preserved. An alternative implementation should have been based on a NuSMV parser instead of using regular expressions.

\section{Evaluation}
\subsection{Validation}
To ensure the correctness our implementation we have tested our prototype on many NuSMV files. We have done a semantic comparison of each LTL property $\psi$ against the special properties:
\begin{itemize}
    \item $\psi$: must yield equivalence
    \item \texttt{TRUE}: must yield \texttt{$\psi$ refines TRUE}
    \item \texttt{FALSE}: must yield \texttt{FALSE refines $\psi$}
    \item \texttt{!$\psi$}: must yield \texttt{incomparable}    
\end{itemize}

These checks are automated in \texttt{AllPropCheckTest.java}. We have inspected all failures and concluded that these result only from $\psi$ being either trivially \texttt{FALSE} or trivially \texttt{TRUE}.

We have further checked special cases where we manually designed pairs of specifications to have fixed comparison outcomes. These checks include 17 LTL specification pairs on 9 models and are automated in \texttt{SpecialCasesTest.java}.
